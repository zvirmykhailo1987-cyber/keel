# Expand-contract і міграції без простою

Також відомо як parallel change. Суть: несумісну зміну розбити на кроки, кожен з яких сумісний із сусідньою версією коду.

## Послідовність на прикладі: перейменувати `name` у `full_name`

| Крок | Схема | Код | Відкат |
|---|---|---|---|
| 1. Expand | додати `full_name`, nullable | не змінено | видалити колонку |
| 2. Dual write | без змін | пише в обидві, читає стару | повернути версію коду |
| 3. Backfill | заповнити `full_name` старих рядків | без змін | не потрібен: можна повторити |
| 4. Перевірка | без змін | порівняти колонки, у логах розбіжності | без змін |
| 5. Переключити читання | без змін | читає нову, пише в обидві | повернути версію коду |
| 6. Припинити запис у стару | без змін | лише нова | повернути крок 5 |
| 7. Contract | видалити `name` | не змінено | лише з бекапу: **незворотно** |

Кроки 1 і 7 розділяють щонайменше повний цикл випуску, включно з фоновими задачами, звітами й партнерами. Перед кроком 7 перевір журнали запитів: чи звертається ще хтось до старої колонки. Stripe описує той самий чотирикроковий шлях для зміни моделі даних у робочій системі: подвійний запис, читання з нового, запис лише в нове, видалення старого.

## Безпека операцій за рушієм

Поведінка залежить від версії. Звір із документацією своєї версії; наведене нижче перевіряй на копії.

### PostgreSQL

- Перед будь-яким `ALTER` у робочій базі постав `SET lock_timeout = '5s'`: `ALTER` чекає в черзі за довгим запитом, а за ним стають усі інші.
- `ADD COLUMN` без дефолту чи зі сталим дефолтом не переписує таблицю (починаючи з версії 11). Нестабільний дефолт (`random()`, `clock_timestamp()`) переписує.
- Індекс: `CREATE INDEX CONCURRENTLY`. Працює поза транзакцією; якщо впав, лишає недійсний індекс, який треба видалити.
- Обмеження: `ADD CONSTRAINT ... NOT VALID`, потім окремо `VALIDATE CONSTRAINT`: перевірка не блокує записів.
- `SET NOT NULL` сканує таблицю; з версії 12 скан пропускається, якщо вже є валідне `CHECK (col IS NOT NULL)`.
- Зміна типу зазвичай переписує таблицю: додай нову колонку за expand-contract.
- Лінтер міграцій: Squawk. Для Rails: `strong_migrations`. Для відкатних схем: pgroll.

### MySQL

- `ALGORITHM=INSTANT` чи `INPLACE` явно: запит упаде, якщо операція неможлива, замість тихої копії таблиці.
- Для великих змін: gh-ost або pt-online-schema-change. Вони копіюють таблицю поступово.
- Метадані блокування також чекають на довгі транзакції.

### SQLite

- `ALTER TABLE` обмежений. Складніші зміни йдуть процедурою з документації: нова таблиця, копіювання, заміна в транзакції.
- `DROP COLUMN` з версії 3.35. Перед застосуванням перевір версію.
- Копія: `VACUUM INTO` або backup API, а не копіювання файла під час запису (WAL).
- Увімкни `PRAGMA foreign_keys` явно й перевір після міграції `PRAGMA foreign_key_check`.

## Порядок випуску

1. Міграція expand перед кодом.
2. Новий код.
3. Міграція contract лише після того, як старого коду ніде немає, включно з фоновими процесами.

Відкат коду можливий лише, поки схема сумісна зі старою версією: це і є головна користь розбиття.

## Backfill

```sql
-- порція за ключем; повторний запуск безпечний завдяки умові IS NULL
UPDATE users SET full_name = name
WHERE id > :last_id AND id <= :last_id + 1000 AND full_name IS NULL;
```

Правила:

- Порціями: не `OFFSET`, а за ключем. Окрема транзакція на порцію.
- Пауза між порціями; стеж за затримкою реплік і навантаженням.
- Зберігай прогрес, щоб продовжити після обриву.
- Ідемпотентний: повтор не псує вже заповнене, особливо значення, змінене новим кодом за цей час.
- Звіт: заповнено, лишилось, причини порожніх.
- Нуль для «невідомо» заборонено: лишай `null`.

## Міграція на копії

Послідовність, що не міняється:

1. Свіжа копія робочого обсягу, анонімізована, якщо копія покидає захищене середовище.
2. Міграція, запис часу, блокування, зміна розміру.
3. Тести застосунку на копії.
4. Лічильники до/після.
5. Прогін відкату, якщо він заявлений.
6. Бекап робочої бази з датою й причиною в імені, перевірка, що він відновлюється.
7. Міграція робочої бази: людина.
8. Звірка ще раз і smoke-тест.

Копія не показує конкурентного навантаження. Кажи про це у звіті; для ризикових кроків плануй вікно малого навантаження й таймаут блокування.

## Міграції в коді

- Файл міграції після застосування не редагується: нова міграція.
- Логіка міграції не імпортує моделі застосунку: вони зміняться. Опиши потрібні поля локально.
- Обчислення не покладається на LLM. Перетворення виконує детермінований код, результат перевіряється лічильниками.
- Дві гілки, що додають міграції: порядок і конфлікти перевір перед злиттям.
