# data-migrations: зміна, яку можна повторити й перевірити

Якщо в pre-flight сесії згадано overlay для цієї навички, прочитай його перед роботою.

## ТЗ-чекліст

«Зміни схему» чи «залий дані» означає пакет. Веди N/N до кінця.

1. Зміну схеми розбито на кроки expand, migrate, contract, якщо є живі споживачі.
2. Файл міграції під контролем версій, із відкатом або причиною, чому відкату немає.
3. Код сумісний зі старою і новою схемою під час викочування.
4. Міграцію й тести прогнано на копії; час і блокування виміряно.
5. Звірка до/після: лічильники й контрольні записи.
6. Імпорт: другий прогін створює 0 нових записів; звіт сходиться.
7. Backfill окремо, ідемпотентний, порціями.
8. План для робочої бази: бекап, порядок, відкат; виконує людина.
9. Документацію схеми й опис джерела оновлено; скан секретів запущено.

## Pre-flight

Прочитай у `${CLAUDE_PLUGIN_ROOT}/data/pitfalls/`:

- G15 «невідомо» стало нулем; G8 арифметика й парсинг на межі; G22 мовчазний дефолт; G57 pandas губить часовий пояс і NaN.
- G19 бекап без маніфесту; G23 число без збереженого входу; G20 перевірено не те місце, куди діє команда.
- G38 запис у генерований файл; G4 копії розходяться; G7 кодування на Windows; G40 перед «непридатне для машини» обійти всі способи доступу.

## Метод

### Зміна схеми

1. **Оціни таблицю:** розмір, швидкість запису, хто читає й пише, версія рушія. Деякі `ALTER` блокують таблицю надовго, навіть якщо виглядають дрібними (`references/expand-contract.md`).
2. **Розбий на expand-contract:**
   - expand: додай нове поруч зі старим, старий код не ламається;
   - migrate: нова версія коду пише в обидва, backfill наповнює, читання перемикається;
   - contract: коли старим ніхто не користується, прибери. Окремий випуск пізніше.
3. **Зроби кожен крок сумісним у часі.** Під час викочування працюють стара й нова версії коду одночасно. Міграція застосовується до нового коду, а видалення лише після зникнення старого.
4. **Прожени на копії робочого обсягу:** міграція, тести застосунку, запис часу. Міряй, а не припускай. Порожня база нічого не доводить. Копію обробляй як робочі дані: не передавай назовні, за потреби знеособ.
5. **Звір до/після:** кількість рядків ключових таблиць, кількість непорожніх у зачеплених колонках, контрольні суми, 3–5 відомих записів через інтерфейс і пошук.
6. **Підготуй план робочої бази:** бекап із причиною в імені, таймаут блокування, порядок, команду відкату. Передай людині (навичка `deploy-ci` для випуску).

### Імпорт

1. **Опиши джерело:** колонки, типи, кодування, унікальність, приклади сміття, дата витягу.
2. **Задай ключ джерела** зі стабільних полів: `source + natural_id`. Не автоінкремент і не хеш усього рядка: найменша правка в джерелі дасть новий запис.
3. **Упиши правила злиття:** порожнє заповнюємо; автоматичне оновлюємо; введене людиною не чіпаємо; конфлікт джерел у звіт.
4. **Не вигадуй відповідність колонок.** Незрозуміла колонка йде у звіт як незмаплена.
5. **Прожени двічі на копії.** Другий прогін: створено = 0. Звіт: прочитано = створено + оновлено + пропущено + відкинуто (з причиною). Не сходиться: імпорт не виконано.
6. Деталі: `references/idempotent-imports.md`.

### Backfill

Окремо від зміни схеми. Порціями з паузою, за ключем, а не `OFFSET`. Можна перервати й продовжити. Лічильники: заповнено, лишилось порожніх і чому. Порожнє лишається `null`, а не `0`.

## Профіль стеку

Команди тестів бери з `.keel/project.toml` і `${CLAUDE_PLUGIN_ROOT}/data/stacks/<id>.toml`, секція `frameworks` підкаже інструмент міграцій. Не вгадуй: перевір, що справді є в проєкті.

| Стек | Міграції | Перевірка |
|---|---|---|
| Python | Alembic, Django migrations | `alembic upgrade head --sql`, `sqlmigrate` |
| Ruby | Rails migrations | `strong_migrations` |
| Java/Kotlin | Flyway, Liquibase | перевірка на копії |
| Go | golang-migrate, goose | перевірка на копії |
| JS/TS | Prisma, Knex | `prisma migrate diff` |
| PHP, C# | Laravel, EF Core | `migrate --pretend`, `dotnet ef migrations script` |

Копія бази: PostgreSQL `pg_dump -Fc` + `pg_restore`; MySQL `mysqldump --single-transaction`; SQLite `VACUUM INTO 'copy.db'`. Upsert: PostgreSQL і SQLite `ON CONFLICT (key) DO UPDATE`; MySQL `ON DUPLICATE KEY UPDATE`.

Скан перед комітом дампів і конфігів (дампи в git не кладуться взагалі):

```sh
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel scan --staged
```

## Автономія

| Дія | Tier | Хто |
|---|---|---|
| Читання схеми, вимір розміру, звіт про джерело | 0 | авто |
| Файл міграції, імпортер, тести, прогін на копії, локальна гілка | 1 | авто |
| Міграція, backfill, імпорт, видалення дублів у робочій базі | 3 | лише людина, після бекапу |
| Push у main, деплой, публікація, гроші, ротація секретів, листи | 3 | лише людина |

Рекомендація злиття дублів показує, які саме записи зіллються. Рішення за людиною.

## Типові збої

- Перейменування одним кроком → стара версія коду падає під час викочування.
- `NOT NULL` зі значенням за замовчуванням на великій таблиці у старій версії рушія → довге блокування.
- Міграція одразу на робочій → копія не використовувалась.
- Повторний імпорт подвоює базу → немає ключа джерела.
- Імпорт затер значення людини → немає правил злиття.
- «Невідомо» стало нулем → фільтри й середні тихо брешуть (G15).
- Кодування: cp1251 прочитано як UTF-8 → кракозябри помічають пізно.
- Дати з Excel: серійні номери, 1900 вважається високосним.
- Backfill в одній транзакції → довге блокування, ріст журналу.
- Індекс пошуку не оновлено → запис є, але не знаходиться.

## Спростування

Назви щонайменше один сценарій, за якого зміна ламає наявну поведінку: стара версія застосунку, фонова задача, звіт, що читає колонку напряму, інтеграція партнера, кешований план запиту. Для імпорту назви причину, чому числа звіту можуть не збігтися з реальністю.

## Гейт «готово»

- Запущено на копії: команда міграції, тести, тривалість, розмір даних копії.
- Виміряно: лічильники до/після, другий прогін імпорту створив 0, рівність звіту сходиться.
- План для робочої бази написано; робочу базу не чіпав.
- Не перевірено: скажи явно (копія менша за робочу, блокування під реальним навантаженням не міряно, відкат не прогнано).
- Без відкату: сказано вголос, чому, що робити, якщо щось пішло не так, і який бекап.

## Ретро

Після міграції запиши через `/keel:retro`: фактичний час проти виміряного на копії, що було неочікувано. Такі дані показують, наскільки копії можна довіряти.
