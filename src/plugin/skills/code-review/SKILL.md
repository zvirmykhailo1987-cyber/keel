# code-review: знахідка без сценарію поломки не є знахідкою

Якщо в pre-flight сесії згадано overlay для цієї навички, прочитай його перед роботою.

## ТЗ-чекліст

«Переглянь зміну» означає пакет. Веди N/N до кінця, у підсумку покажи рахунок.

1. Межі зміни названо: база, голова, кількість файлів і рядків.
2. Намір зміни відомо або припущення записано.
3. Змінені функції прочитано повністю, а викликачів публічних символів знайдено.
4. Пройдено всі пʼять проходів методу.
5. Лінтер, типи й тести запущено або сказано, чому ні.
6. Скан секретів запущено на змінених файлах.
7. Знахідки подано масивом за схемою `schemas/code-review-finding.schema.json`.
8. Вердикт і перелік непереглянутого написано.

## Pre-flight

Перед великим ревʼю прочитай у `${CLAUDE_PLUGIN_ROOT}/data/pitfalls/` записи, що стосуються:

- G3 секрети в репозиторії; G8 арифметика й парсинг без граничних тестів; G15 «невідомо» стало нулем; G22 мовчазний дефолт на неохайному вході.
- G6 документація розходиться з кодом; G25 побічний ефект під час імпорту; G38 правка генерованого файла; G20 і G60 перевірка дивиться не туди.
- G52 тест є, але ніде не запускається; G10 обіцяне в описі PR не доведено до кінця.
- Зміна фронтенду: додатково G17, G27–G37, G41.

## Метод

1. **Визнач межі.** База зміни береться з PR або запитується: `git diff --stat <база>...HEAD`, `git log --oneline <база>..HEAD`. Для незакоміченого: `git diff` і `git diff --staged`. Запиши розмір.
2. **Обмеж порцію.** Понад 400 рядків логіки за раз ревʼю втрачає якість: дослідження SmartBear і Cisco радить 200–400. Розбий за шаром або за комітами й скажи, що саме переглянуто в цій порції. Генеровані файли й lockfile позначай окремо, а не читай рядок за рядком.
3. **Зʼясуй намір.** Опис PR, задача, повідомлення комітів. Намір невідомий: виведи його з diff і запиши як припущення. Код, що правильно робить не те, що просили, теж є дефектом.
4. **Читай ширше за diff.** Прочитай функцію цілком. Для кожного зміненого публічного символу знайди викликачів пошуком за іменем. Зміна контракту без зміни викликачів є найчастішим дефектом, якого не видно в diff.
5. **Пройди пʼять проходів окремо,** не змішуючи їх (питання кожного в `references/review-checklist.md`):
   - коректність: межі, null, порядок, конкурентність, транзакції, обробка помилок;
   - безпека: авторизація об'єкта, ін'єкції, секрети, небезпечні дефолти;
   - дані й сумісність: міграція, формат API, конфігурація, старі клієнти;
   - тести: чи червоніє новий тест без зміни, чи покрито негативну гілку;
   - супровід: лише те, що має наслідок (дублювання, яке розійдеться; мертва гілка).
6. **Доведи кожну знахідку.** Напиши конкретні вхід і стан, потім неправильний вихід. Де дешево, відтвори: одноразовий тест або запуск. Не відтворив: почни `failure_scenario` зі слів «Не відтворено запуском:».
7. **Відсій.** Викинь знахідки без сценарію, зауваження зі смаку і те, що ловить лінтер (замість цього запусти лінтер). Сумнів щодо наміру автора формулюй питанням у підсумку, а не дефектом.
8. **Перевір перед вердиктом,** що змінений `file:line` існує в поточній голові: рядок після ребейзу міг зсунутися.
9. **Видай результат:** спершу JSON-масив, найсерйозніші зверху, далі короткий текст людською мовою: вердикт, рахунок N/N, що не переглянуто.

### Формат знахідки

Поля: `file`, `line`, `category`, `failure_scenario`, `severity`, `fix`, `needs_confirmation`. Схема сувора, зайві поля заборонені.

```json
[{
  "file": "src/billing/invoice.ts",
  "line": 42,
  "category": "correctness",
  "failure_scenario": "Замовлення з порожнім items: reduce без початкового значення кидає TypeError, сторінка рахунку віддає 500 для кожного нового клієнта.",
  "severity": "high",
  "fix": "Додати початкове значення: items.reduce((sum, i) => sum + i.total, 0), і тест на порожній список.",
  "needs_confirmation": false
}]
```

`needs_confirmation: true` став, якщо виправлення зачіпає незворотне: міграцію робочої бази, деплой, ротацію секрету, видалення даних.

Погано: «тут можлива проблема з null». Добре: «`user.profile` порожній для акаунтів, створених до міграції додавання профілю: `user.profile.name` кидає виняток на `/settings`». Шкала severity і більше прикладів у `references/review-checklist.md`.

## Профіль стеку

Команди не вгадуй. Прочитай `.keel/project.toml`, потім `${CLAUDE_PLUGIN_ROOT}/data/stacks/<id>.toml` (секція `[commands]`, а також `pitfalls`). Немає `.keel/project.toml`: визнач стек за маркерами файлів зі списку профілів і скажи про це.

Запуск рушія:

```sh
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel scan src/changed_file
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel scan --staged
```

Що шукати за мовою, коротко:

- Python: змінний дефолт аргументу; `except:` без типу; `open()` без `encoding`.
- JavaScript/TypeScript: забутий `await`; `==` проти `===`; `any`, що ховає `undefined`.
- Go: проігнорована `err`; захоплення змінної циклу в горутині у версіях до 1.22; `defer` у циклі.
- Rust: `unwrap()` на шляху із зовнішнім входом; `unsafe` без обґрунтування інваріанта.
- Java/Kotlin/C#: неперехоплений null на межі з бібліотекою; незакритий ресурс; помилки в `async void` у C#.

## Автономія

| Дія | Tier | Хто |
|---|---|---|
| Читання коду, diff, запуск лінтера, типів, тестів, скану | 0 | авто |
| Звіт зі знахідками, одноразовий тест-відтворення, правка на локальній гілці з тестом | 1 | авто |
| Коментарі в чужому PR, схвалення чи відхилення PR | 3 | людина |
| Push у main, злиття, деплой, публікація, міграція робочої бази, гроші, ротація секретів, листи | 3 | лише людина |

Вердикт «можна зливати» є думкою. Сам злиття не виконує.

## Типові збої

- Абстрактне зауваження без входу → перепиши зі сценарієм або викинь.
- Прочитано лише рядки diff → дефект у контракті з викликачем пропущено; читай викликачів.
- Лавина дрібниць ховає один критичний дефект → відсій, сортуй за severity.
- Тест зелений, бо нічого не перевіряє → спитай, чи червоніє він без зміни (G52, G60).
- Правка генерованого файла → виправляти треба джерело генерації (G38).
- Галюцинований імпорт чи метод у згенерованому коді → знайди символ у залежності, а не вір назві.

## Спростування

Для кожної зміни назви щонайменше один сценарій, за якого вона ламає наявну поведінку: старий клієнт, старий рядок у базі, конкурентний виклик, порожній вхід, інша ОС. Перевірив і не знайшов: так і напиши, що саме перевіряв. Hyrum's Law: якщо поведінку видно, хтось на неї покладається, навіть коли її немає в контракті.

Для власного висновку «дефектів немає» назви, яку категорію дефектів це ревʼю не могло виявити (наприклад, продуктивність під навантаженням).

## Гейт «готово»

- Запущено: перелічи команди й результат кожної (кількість тестів, код виходу).
- Виміряно: розмір diff, файли переглянуто N із M.
- JSON проходить схему: `line` указує на наявний рядок, сценарій конкретний.
- Не перевірено: скажи явно (тести потребують зовнішнього сервісу, файл пропущено, поведінку під навантаженням не міряно).
- Немає даних про намір: сказано, а не вгадано.

## Ретро

Після великого ревʼю дефект, який повторюється або який дивом не дійшов до робочого середовища, оформи уроком через `/keel:retro`: помилка, перевірене рішення, доказ.
