# Питання для пʼяти проходів ревʼю

Кожне питання має вести до конкретного сценарію. Відповідь «так, це можливо» без входу ще не знахідка.

## Шкала severity

| Рівень | Критерій | Приклад |
|---|---|---|
| critical | втрата чи витік даних, обхід авторизації, неможливість відкоту | запит повертає рахунки іншого клієнта |
| high | основний сценарій ламається для частини користувачів | сторінка падає для порожнього кошика |
| medium | рідкісний сценарій або є обхід | подвійний клік створює дублікат, який легко видалити |
| low | наслідок є, але незначний | застаріла підказка, повідомлення помилки вводить в оману |

Смак не має рівня. Без наслідку знахідки немає.

## Прохід 1: коректність

- Що станеться на порожньому вході, одному елементі, дублікаті, максимальному розмірі?
- Ділення: знаменник може бути нулем чи майже нулем? Гроші рахуються в float?
- Null, None, undefined, порожній рядок: чи не змішано «невідомо» з нулем?
- Час: часовий пояс, кінець місяця, 29 лютого, літній час, годинник клієнта?
- Порядок: чи покладається код на порядок ключів, файлів чи рядків без ORDER BY?
- Помилки: що бачить користувач, коли зовнішній виклик упав? Виняток проковтнуто?
- Повторний виклик: повторна доставка чи подвійний клік створює дублікат?
- Конкурентність: два запити між читанням і записом (check-then-act)? Спільний змінний стан?
- Транзакція: часткове виконання лишає дані неузгодженими? Зовнішній виклик усередині транзакції?
- Ресурси: чи закрито файл, зʼєднання, таймер на гілці помилки?

## Прохід 2: безпека

- Об'єкт з ідентифікатором із запиту: чи перевірено, що він належить цьому користувачу?
- Перевірка прав є в кожному новому маршруті, чи лише в інтерфейсі?
- Запит, шлях, команда, HTML збираються конкатенацією із зовнішнього входу?
- URL від користувача йде на серверний запит (SSRF)?
- Секрет у коді, логах, повідомленні помилки, URL?
- Нова залежність реально існує й потрібна? Імʼя не схоже на популярний пакет?
- Глибина: аудит цілого застосунку веде навичка `security`.

## Прохід 3: дані й сумісність

- Міграція працює зі старою версією коду під час викочування?
- Поле стало обовʼязковим: що зі старими рядками й старими клієнтами?
- Змінено формат API, подію, ключ кешу, файл: хто читає старий формат?
- Нова змінна оточення: дефолт безпечний чи застосунок має впасти при старті?
- Дефолт конфігурації змінює поведінку наявних інсталяцій?

## Прохід 4: тести

- Чи червоніє новий тест, якщо відкотити зміну? Запусти, коли дешево.
- Є негативний сценарій, чи лише щасливий шлях?
- Мок не ховає той самий контракт, який змінено?
- Новий тест реально запускається в CI чи локальній команді (файл, префікс, маркер)?
- Час, випадковість, мережа в тесті роблять його нестабільним?

## Прохід 5: супровід

Лише з наслідком:

- Дублювання правила в двох місцях, які розійдуться при наступній зміні.
- Мертва гілка або прапорець, який ніколи не вмикається.
- Назва каже протилежне до поведінки.
- Заглушка TODO у шляху, який виконується в робочому середовищі.
- Опис PR чи README більше не відповідає коду.

## Погані й добрі формулювання

| Погано | Добре |
|---|---|
| Варто додати обробку помилок | `fetchRate` падає за таймаутом: виняток не перехоплено в `checkout:88`, клієнт бачить 500, хоч ціну можна взяти з кешу |
| Потенційна SQL-ін'єкція | `q` з URL вставлено у f-рядок у `search.py:31`: `q=' OR 1=1 --` поверне всю таблицю |
| Може бути race condition | Два запити `POST /redeem` між читанням `used` і записом у `coupon.go:57` використають купон двічі |
| Складний код | Умову скидання знижки продубльовано в `cart.rb:20` і `order.rb:64`, нова правка в одному місці дасть різну суму в кошику й замовленні |

## Згенерований код

Окремий прохід, якщо зміну писала модель: імпорти й методи, яких немає в залежності; заглушки; вигадані прапорці CLI; тавтологічні тести; секрети в прикладах; код не в стилі сусіднього.
