# debugging: спершу корінь, потім фікс

Якщо в pre-flight сесії згадано overlay для цієї навички, прочитай його перед роботою.

## ТЗ-чекліст

«Полагодь баг» означає пакет. Веди N/N до кінця.

1. Відтворення записано: кроки, команда або тест.
2. Корінь названо одним реченням: «X відбувається, бо Y».
3. Інші місця того самого патерну знайдено.
4. Падаючий тест написано й побачено червоним.
5. Фікс мінімальний, тест зелений, решта тестів зелена.
6. Журнал гіпотез є для нетривіального випадку.
7. Скан секретів перед комітом запущено.
8. Документацію чи README оновлено, якщо вони описували стару поведінку.

Для очевидної друкарської помилки чотири фази зайві: досить фіксу й прогону тестів.

## Pre-flight

- G7 кодування й шляхи на Windows; G45 інструмент виміру бреше в Git Bash; G46 текст через heredoc приходить не байт-у-байт.

- G9 памʼять чи нотатка описує старий стан; G20 перевірка дивиться не туди; G57 pandas губить часовий пояс.

## Метод

Деталі кожної фази й приклади в `references/root-cause.md`. Фази не перескакуй.

**Фаза 1: докази.** Збери точний текст помилки зі стеком, версію й оточення, останній крок, де поведінка ще правильна, потік даних «вхід → шар → вихід». Закріпи відтворення. Поки корінь не названо одним реченням, фікси не пропонуй.

**Фаза 2: патерн.** Знайди робочий приклад поруч і порівняй із зламаним. Пошуком знайди, де ще так само. Фікс лише в одному місці означає повернення бага в іншому.

**Фаза 3: гіпотези, по одній.** Кожна гіпотеза складається з твердження й дешевої перевірки, яка може її вбити. За раз змінюй одну річ, інакше невідомо, що подіяло. Веди журнал:

| Гіпотеза | Перевірка | Результат | Вердикт |
|---|---|---|---|
| Кеш віддає старий запис | Вимкнути кеш, повторити | Збій лишився | Хибна |

**Фаза 4: фікс.** Спершу падаючий тест: мінімальне відтворення, а якщо фреймворку немає, одноразовий скрипт. Побач його червоним саме з очікуваної причини. Потім фікс, тоді прогін: цей тест зелений, решта зелена. Без тесту фікс лише здається робочим.

### Стоп після трьох

Три фікси поспіль не прибрали симптом: зупинись, четвертий не пиши. Це ознака, що проблема не локальна: межі шарів, модель даних чи припущення про порядок подій. Запиши, що відомо напевно, що виключено, і сформулюй архітектурну гіпотезу. Рішення приймай разом із людиною; за потреби перейди до навички `architecture`.

### Прискорювачі локалізації

- Регресія: `git bisect run <команда тесту>` за логарифмічну кількість кроків знаходить коміт.
- Великий вхід: зменшуй половинним поділом до найменшого, що ще падає.
- Нестабільний збій: повторюй у циклі й рахуй частоту до й після фіксу (`references/root-cause.md`).
- Інше оточення: порівняй версію, конфігурацію, дані, часовий пояс, кодування, ОС.

## Профіль стеку

Команди тестів бери з `.keel/project.toml` і `${CLAUDE_PLUGIN_ROOT}/data/stacks/<id>.toml`, секція `[commands]`; там само `pitfalls` стеку. Без профілю скажи, що визначив команду за маркерами проєкту.

Інструменти за мовою:

| Мова | Зупинка й стан | Гонки й памʼять |
|---|---|---|
| Python | `breakpoint()`, `python -X faulthandler` | `tracemalloc` |
| JavaScript/TypeScript | `node --inspect-brk`, `--trace-uncaught` | `--heapsnapshot-signal` |
| Go | `dlv test`, `GOTRACEBACK=all` | `go test -race` |
| Rust | `RUST_BACKTRACE=1`, `rust-gdb` | Miri, TSan на nightly |
| C/C++ | `gdb`, `lldb`, `rr` на Linux | `-fsanitize=address,thread,undefined` |
| Java/Kotlin | `jstack`, віддалений налагоджувач | `jcmd`, heap dump |
| .NET | `dotnet-dump`, `dotnet-trace` | `dotnet-counters` |

Скан секретів перед комітом:

```sh
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel scan --staged
```

Логи, дампи й стеки можуть містити токени й персональні дані. Перед вставкою в нотатку чи звіт перевір їх цією ж командою за шляхом файла.

## Автономія

| Дія | Tier | Хто |
|---|---|---|
| Читання логів, коду, історії; запуск тестів, налагоджувача на локальній копії | 0 | авто |
| Падаючий тест, фікс із тестом, діагностичний вивід, локальна гілка | 1 | авто |
| Діагностика на робочому середовищі, зміна конфігурації робочого сервера | 3 | людина |
| Push у main, деплой, публікація, міграція робочої бази, гроші, ротація секретів, листи | 3 | лише людина |

Незворотна дія заради перевірки гіпотези, навіть «лише подивитися», теж Tier 3: зроби її на копії.

## Типові збої

- Фікс симптому: додано перевірку на null, а звідки null, ніхто не знає → повернись до фази 1.
- Дві зміни одночасно → невідомо, що подіяло; відкоти одну.
- «Тепер працює» без відтворення → збій міг просто не проявитись; покажи червоний тест.
- Вірити коментарю, нотатці, памʼяті замість коду (G9) → перевір на поточному стані.
- Зміна таймауту чи повтор замість пояснення гонки → маскування.
- Діагностичний вивід лишився в коді → прибрати перед комітом.
- Вимкнено падаючий тест, щоб стало зелено → це приховування, а не фікс.

## Спростування

Назви щонайменше один сценарій, за якого цей фікс ламає наявну поведінку: хто покладався на стару помилкову поведінку, чи змінюється формат виходу, чи не повільніше на гарячому шляху. Назви також, що могло б спростувати твій корінь: який факт не пояснюється. Такий факт є: корінь іще не знайдено.

## Гейт «готово»

- Запущено: падаючий тест до фіксу (вивід червоного) і після (зелений), повний набір тестів.
- Нестабільний збій: виміряно частоту до й після на однаковій кількості повторів.
- Корінь названо одним реченням, патерн перевірено пошуком.
- Не перевірено: скажи явно (наприклад, відтворено лише локально, на робочому середовищі не перевіряв).
- Не вдалося знайти корінь: так і скажи, разом із журналом гіпотез, а не подавай здогад як висновок.

## Ретро

Після складного збою оформи урок через `/keel:retro`: симптом, справжній корінь, яка перевірка знайшла б його раніше. Повторний клас збою варто перетворити на тест чи правило лінтера.
