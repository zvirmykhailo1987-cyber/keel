# Чотири фази кореня: розгортка

Метод спирається на систематичне налагодження з `obra/superpowers` і на розділ про усунення збоїв у книзі Google SRE. Посилання в `techniques.md`.

## Фаза 1: докази

Спочатку прочитай помилку до кінця. Найнижчий рядок стека твого коду часто важливіший за верхній.

Запиши:

- точний текст і код виходу, без переказу;
- версії: мови, залежностей, ОС, коміт;
- останній відомий робочий стан: коміт, дата, конфігурація;
- що змінилось між робочим і зламаним станом: `git log`, оновлення залежностей, дані, оточення;
- де дані ще правильні: додай вивід на межах шарів і знайди перший неправильний.

**Відтворення.** Найкорисніший результат фази. Спрощуй його, поки кожен крок не став потрібним. Не вдається відтворити: збирай дані (логи, частота, умови), а не вгадуй фікс.

Між системами перевіряй межі: запит, який справді пішов; відповідь, яка справді прийшла; значення конфігурації, яке реально прочитано. Не те, що мало бути.

## Фаза 2: патерн

- Знайди робочий аналог у тому самому коді. Перелічи всі відмінності, навіть дрібні.
- Шукай ту саму конструкцію пошуком: `None` без перевірки, той самий запит, та сама формула.
- Прочитай документацію бібліотеки для конкретної версії, а не памʼять про неї.

## Фаза 3: гіпотези

Формулюй так: «Якщо X є причиною, то перевірка Y дасть Z». Обирай найдешевшу перевірку, яка може спростувати. Спростувати цінніше, ніж підтвердити: підтвердження часто збігається випадково.

Порядок пошуку:

1. Що змінилось нещодавно.
2. Власний код, потім чужий. Помилка в компіляторі чи популярній бібліотеці можлива, але малоймовірна.
3. Дані й оточення: кодування, часовий пояс, порожні значення, права, місце на диску.
4. Час і порядок: гонки, кеш, застарілі файли збірки.

Половинний поділ простору пошуку кращий за послідовний перебір:

```sh
git bisect start
git bisect bad HEAD
git bisect good <робочий-коміт>
git bisect run <команда-що-падає-лише-на-зламаному>
```

Зміна поведінки пропала, щойно ти додав вивід? Це типова ознака гонки, а не «полагодилось».

## Фаза 4: фікс

1. Напиши падаючий тест на найнижчому шарі, де відтворюється.
2. Запусти й переконайся, що він падає з очікуваної причини. Падіння через помилку в самому тесті нічого не доводить.
3. Зроби найменшу правку на рівні кореня, а не там, де проявився симптом.
4. Запусти цей тест, потім увесь набір.
5. Виправ решту місць із фази 2.
6. Прибери діагностичний вивід.

Немає тестової інфраструктури: одноразовий скрипт із кодом виходу, збережений поруч із задачею, і явна фраза «постійного тесту немає».

## Стоп після трьох невдалих фіксів

Лічильник: фікс, який ти застосував, запустив і який не прибрав симптом або створив новий. Після третього:

1. Припини правити код.
2. Запиши: що спостерігається, які гіпотези виключено й чим.
3. Перевір ознаки архітектурної причини: кожен фікс вилазить в іншому місці; потрібні зміни в багатьох модулях; стан розмазано між шарами; модель даних не виражає потрібну умову.
4. Опиши людині вибір: продовжити локально з новою гіпотезою чи змінити структуру.

## Нестабільний збій

- Замір частоти: запусти N разів і порахуй падіння. Без цього числа неможливо довести, що фікс подіяв.

```sh
# Go
go test -run TestName -count=200 -race -shuffle=on ./pkg
# pytest (повтор скриптом, щоб не додавати плагінів)
for i in $(seq 1 200); do pytest -q tests/test_x.py::test_y || echo FAIL; done | grep -c FAIL
```

- Якщо збій рідкісний, кількість повторів підбирай так, щоб до фіксу він зʼявлявся кілька разів: нуль падінь після фіксу з малого N нічого не доводить.
- Під навантаженням чи обмеженням CPU гонки проявляються частіше. Перевір порядок тестів і спільний стан.

## Збій лише в робочому середовищі

- Читай журнали й метрики навколо часу збою, починаючи зі зміни, випуску, навантаження.
- Склади список відмінностей від локального оточення.
- Спочатку зменш шкоду, якщо є: відкат випуску чи вимкнення прапорця є рішенням людини (Tier 3). Корінь шукай потім, зберігши докази.
- Копію даних для відтворення обробляй як конфіденційну.

## Коли зупинитись на «невідомо»

Якщо часу на корінь немає, чесний результат виглядає так: що відомо, що виключено, тимчасове зменшення шкоди, де вона позначена в коді, і відкрита задача. Не називай це виправленим.
