# Продуктивність

Головне правило: без виміру до зміни немає оптимізації, є лише правка коду. Припущення про «повільне місце» перевіряємо профайлером, а не досвідом.

## ТЗ-чекліст (пакет N/N)

Запит «прискор» означає пакет, а не правку. Веди відповідність до кінця роботи:

1. Сценарій користувача і де болить.
2. Метрика й ціль: перцентиль (p95/p99), пропускна здатність або пам'ять, поріг.
3. Базова лінія зі збереженими командою, SHA, входом і середовищем.
4. Профіль або план запиту, що вказує на конкретне місце.
5. Одна зміна на один вимір.
6. Повторний вимір тим самим способом, з розкидом.
7. Запобіжник від регресу: бюджет у CI або тест на кількість запитів.
8. Звіт: було, стало, що не перевірено.

## Pre-flight

- **G16** інструмент перевірки сам не перевірений: спершу дай профайлеру очевидно повільний код.
- **G17** вимір раніше, ніж система стала тим, що міряють: розігрів, кеш, завершення фонової роботи.
- **G20** гейт дивиться не туди, куди діє команда: чи це та збірка, той сервер, та база.
- **G22** мовчазний дефолт на неохайному вході: мала вибірка, порожня таблиця, debug-збірка.
- **G23** число без збереженого входу не можна відтворити, тому це не результат.
- **G45** інструмент виміру бреше в Git Bash: на Windows звір вимір в іншій оболонці.
- **G15** «не виміряно» не дорівнює нулю.
- **G36** той самий прогін дає різний вердикт: це шум, спершу зменш його.

## Метод

**1. Рамка.** Назви сценарій, метрику й ціль. Цілі немає: запитай або запропонуй її окремо від оптимізації. Без цілі не зрозуміло, коли зупинитись.

**2. Базова лінія.** Release-збірка, дані реалістичного обсягу, зафіксований стан кешу (холодний чи теплий). Кілька прогонів, у звіті p50, p95, p99 і розкид, а не середнє. Запиши команду, SHA, вхід, середовище.

**3. Локалізація згори вниз.**
- Ресурси: метод USE (завантаження, насичення, помилки для CPU, пам'яті, диска, мережі).
- Сервіс: частота, помилки, тривалість за ендпоінтами.
- Код: семплювальний профайлер у режимі, близькому до робочого, потім flame graph. Широкий кадр важливий, високий не обов'язково.
- CPU-профіль мало що покаже, якщо час іде на очікування: потрібен off-CPU, трасування або статистика бази.

**4. База даних.**
- N+1 шукай лічильником, а не секундомером. Той самий запит з 1 і з 50 рядками: кількість SQL не має рости з N. Це ж і є тест-запобіжник.
- `EXPLAIN (ANALYZE, BUFFERS)` у PostgreSQL на копії даних. `ANALYZE` справді виконує запит: для запису лише в транзакції з відкатом і не на робочій базі.
- Сумарне навантаження: `pg_stat_statements` або аналог. Часто шкодить не найповільніший запит, а найчастіший.
- Лікування за порядком: зайві дані (проєкція, пагінація), eager loading або батчинг, індекс, денормалізація. Індекс сповільнює запис: міряй і його.

**5. Кеш лише після локалізації.** Спершу дай відповіді:
- Ключ: чи входить туди користувач, тенант, мова. Помилка тут це витік чужих даних, а не повільність.
- Інвалідація: хто й коли скидає; що побачить користувач у вікні застарілості.
- Лавина: що станеться, коли популярний ключ протух під навантаженням.
- Метрика hit rate. Без неї кеш не доведений.
- HTTP: `Cache-Control`, `ETag` за RFC 9111, а не власний кеш, якщо можна.

**6. Зміна й повторний вимір.** Одна зміна, той самий спосіб виміру. Різниця менша за розкид означає «ефекту не виявлено». Для мікробенчмарків статистичне порівняння (`benchstat`, `hyperfine`, Criterion).

**7. Бюджети.** Час у спільному CI шумить. Стабільніше тримати лічильники: кількість запитів, алокації, розмір бандла, кількість викликів. Час міряй на виділеній машині або порівнюй відносно базової лінії з тієї самої машини.

**8. Навантажувальний тест.**
- Відкрита модель: постійна частота приходу (`constant-arrival-rate` у k6), бо закрита модель приховує чергу (coordinated omission).
- Відкинь розігрів; переконайся, що не генератор навантаження є вузьким місцем (його CPU, порти).
- Підіймай до точки перегину, де p99 різко росте. Результат: «X rps при p99 < Y», а не «витримав X rps».
- Обсяг даних і конфігурація як у проді, інакше результат переноситься слабко.

## Профіль стеку

Стеки проєкту візьми з `stacks` у `.keel/project.toml`, команди збірки й тестів із `[commands]` у `${CLAUDE_PLUGIN_ROOT}/data/stacks/<id>.toml`, а також `pitfalls` і `maturity` звідти. Профайлерів у профілях немає, тому орієнтир нижче. Перед запуском звір прапори з документацією встановленої версії.

| Стек | CPU | Пам'ять або інше |
|---|---|---|
| python | `py-spy record`, `cProfile` | `memray` |
| javascript | `node --cpu-prof`, DevTools | heap snapshot у DevTools |
| go | `go test -bench=. -cpuprofile cpu.out`, `go tool pprof` | `-memprofile`, `benchstat` |
| java, kotlin | async-profiler, JFR | JFR, heap dump |
| dotnet | `dotnet-trace` | `dotnet-counters`, `dotnet-gcdump` |
| ruby | `rbspy` | немає перевіреного дефолту, дивись документацію фреймворку |
| rust | `samply`, `cargo flamegraph` | Criterion для бенчмарків |
| cpp | `perf` (лише Linux), `samply` | Valgrind |
| php | Xdebug у режимі профілювання | немає перевіреного дефолту |
| swift | Instruments (лише macOS) | Instruments, Allocations |

Для стеку поза таблицею або з `maturity = "beta"` так і скажи: глибина менша.

## Автономія

| Tier | Дія | Хто |
|---|---|---|
| 0 | Читання коду, профіль локально, `EXPLAIN` без `ANALYZE` | авто |
| 1 | Нотатка, урок, чернетка бюджету | авто, з відкатом |
| 2 | Оптимізація й тест на локальній гілці, без злиття; навантаження лише на власне локальне середовище | авто |
| 3 | Навантаження на прод або чужий сервіс, зміна конфігурації проду, міграція робочої бази (зокрема індекс), push у main, деплой, гроші, секрети, листи | лише людина |

Навантажувальний тест на чужий сервіс без згоди його власника схожий на атаку.

## Типові збої

- Оптимізація без базової лінії: ефект не довести.
- Debug-збірка, порожня база або теплий кеш дають число ні про що.
- Середнє ховає хвіст; десять викликів по p99 у межах одного запиту роблять хвіст звичайним.
- Закрита модель навантаження малює низьку затримку під час затору.
- Кеш лікує симптом і приносить застарілі дані.
- Мікробенчмарк вимірює те, що компілятор викинув.

## Спростування

Перед висновком назви щонайменше одну причину, чому результат може бути хибним, і перевір її. Типові кандидати: приріст дав теплий кеш, змінилось навантаження сусідів, вибірка замала, профайлер спотворив картину. Прогнати порівняння у зворотному порядку дешево й часто розвінчує «прискорення».

## Гейт «готово»

Готово, лише коли є дві цифри одним способом виміру, з командою, SHA й розкидом, і запобіжник від регресу. У звіті окремо: що виміряно, на яких даних і де; що не перевірено (прод, інша ОС, реальний обсяг). Немає виміру після зміни: кажи «не перевірено», а не «швидше».
