# architecture: вибір за обмеженнями, а не за модою

Якщо в pre-flight сесії згадано overlay для цієї навички, прочитай його перед роботою.

## ТЗ-чекліст

«Спроєктуй» означає пакет. Веди N/N до кінця.

1. Рушій рішення названо: що змінилось чи болить зараз, з вимірами, якщо є.
2. Обмеження зафіксовано: навантаження, команда, час, бюджет, сумісність, комплаєнс.
3. Варіанти: щонайменше два плюс «нічого не міняти».
4. Порівняння за обмеженнями, а не за загальними перевагами.
5. Оборотність рішення оцінено.
6. ADR-чернетку записано.
7. Межі модулів мають автоматичну перевірку або явну причину її відсутності.
8. План переходу малими кроками з точками відкоту, без втрати робочого стану.
9. Сценарій спростування написано.

## Pre-flight

Прочитай у `${CLAUDE_PLUGIN_ROOT}/data/pitfalls/`:

- G1 перша версія без глибини; G24 вимога без інструменту її виконання; G14 «неможливо» до вичерпного пошуку.
- G4 копії коду розходяться; G18 скрипт копіюють, і фікс не доходить; G38 правка генерованого файла; G25 побічний ефект імпорту.
- G6 документація розходиться з кодом; G9 нотатка описує старий стан; G26 нове правило не доходить до наступних сесій.
- G23 число без збереженого входу; G44 продукт живе лише на диску; G13 обхід уже наявної системи.

## Метод

1. **Прочитай наявне.** Структура, залежності, історія змін, наявні ADR, документація. Перевір за кодом, що документ ще правдивий. Для малих зрушень спершу пошукай, чи є вже такий механізм у проєкті.
2. **Назви рушій.** Одним абзацом, що вимагає рішення. «Хочемо мікросервіси» не рушій. «Дві команди блокують одна одну на релізах: 3 з 5 останніх випусків затримались через чужий модуль» рушій. Немає даних: так і скажи й запропонуй, що виміряти.
3. **Випиши обмеження й сортуй.** Спершу тверді (закон, бюджет, наявна база, навички команди), потім бажані. Кількісні мають число чи діапазон із джерелом або позначені «припущення».
4. **Згенеруй варіанти.** Обовʼязково: нічого не міняти; найпростіший, що знімає рушій; один справді інший. Не показуй очевидного переможця з двома опудалами.
5. **Порівняй у таблиці**: рядки є обмеженнями, а не абстрактними чеснотами. Для чисел: виміряй на прототипі або познач як оцінку. Шаблон у `references/adr-and-decisions.md`.
6. **Оціни оборотність.** Легко відкотити: вибирай швидше й простіше. Важко (формат даних, публічний API, базова платформа): глибше перевір, став точку перегляду. Нудна технологія, яку команда знає, зазвичай виграє, якщо нова не знімає конкретне обмеження.
7. **Запиши ADR:**

   ```sh
   echo '{"action":"draft_adr","params":{"project":"<id>","title":"Коротке рішення","context":"Рушій і обмеження","decision":"Що обрано й чому","consequences":"Плюси, ціна, умова перегляду"},"why":"Рішення змінює межі модулів","source":"сесія"}' \
     | sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel propose
   ```

   Рушій пише чернетку у vault, а не в репозиторій. Якщо проєкт тримає ADR у `.keel/adr/` чи `docs/adr/`, скопіюй туди за згодою.
8. **Визнач межі модулів** (`references/module-boundaries.md`): що модуль приховує, його публічний інтерфейс, напрям залежностей, власник даних. Перевірка повинна бути виконуваною: правило в CI, а не абзац у вікі.
9. **Сплануй перехід малими кроками.** Strangler fig, branch by abstraction, expand-contract. Кожен крок можна випустити й відкотити. Рефакторинг окремо від зміни поведінки. Заморожування всієї розробки заради переписування не пропонуй без дуже вагомих причин.
10. **Перевір прототипом** найризикованіше припущення до повного плану.

## Профіль стеку

Команди збірки й тестів бери з `.keel/project.toml` і `${CLAUDE_PLUGIN_ROOT}/data/stacks/<id>.toml`; секція `frameworks` підкаже наявні опори. Навичка не прив'язана до мови.

Перевірка меж за мовою:

| Мова | Вбудовано | Інструмент |
|---|---|---|
| Python | немає | import-linter |
| JavaScript/TypeScript | поля `exports` пакета, project references | dependency-cruiser |
| Go | каталог `internal/` | компілятор сам відхиляє імпорт |
| Rust | крейти, `pub(crate)` | межі workspace |
| Java/Kotlin | модулі Gradle/Maven, JPMS | ArchUnit |
| C# | посилання між проєктами, `internal` | тести на посилання |

## Автономія

| Дія | Tier | Хто |
|---|---|---|
| Читання, виміри, карта залежностей, порівняння варіантів | 0 | авто |
| ADR-чернетка у vault (`draft_adr`), прототип, рефакторинг із тестами на локальній гілці | 1 | авто |
| Прийняття важковідкотного рішення, зміна публічного API чи платформи | 3 | людина вирішує, ти готуєш варіанти |
| Push у main, деплой, публікація, міграція робочої бази, гроші, ротація секретів, листи | 3 | лише людина |

## Типові збої

- Рішення від технології, а не від обмеження → поверни до рушія.
- Розподілена система для команди, якій вистачить модульного моноліту → мережа, узгодженість і оператор додають ціну, яка має щось окупати.
- Абстракція на один випадок (YAGNI) → дочекайся другого реального.
- ADR пишеться заднім числом без відхилених варіантів → майбутній читач повторить обговорення.
- Правило меж лише в документі → через місяць порушене.
- Копія модуля замість спільного джерела → копії розходяться (G4).
- Велике переписування без проміжних випусків → ризик накопичується до дня перемикання.
- Числа про навантаження із загальних блогів → виміряй своє або познач як припущення.

## Спростування

Назви щонайменше один сценарій, за якого рішення ламає наявну поведінку: споживач старого API, фонова задача, що покладається на спільну базу, порядок подій, який гарантував моноліт. Назви також умову, за якої рішення виявиться помилковим, і метрику, що про це скаже; це умова перегляду ADR.

## Гейт «готово»

- Запущено: прототип чи вимір, команда, число. Немає виміру: сказано, що оцінка.
- ADR-чернетка існує: id результату `propose`.
- Перевірка меж запущена, вона падає на навмисному порушенні.
- План кроків: кожен випускається й відкочується окремо.
- Не перевірено: скажи явно (навантаження не міряно, сумісність із клієнтом X не перевірено).

## Ретро

Переглядай ADR за умовою перегляду. Помилковий вибір або вдалий компроміс оформи уроком через `/keel:retro`: припущення, що виявилось, що зміниш наступного разу.
