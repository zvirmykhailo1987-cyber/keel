# Межі модулів і поступовий перехід

## Що таке хороша межа

Модуль приховує рішення, яке може змінитись (принцип Парнаса), а не просто групує файли за типом. Ознаки:

- Зміна всередині не вимагає змін зовні.
- Публічний інтерфейс менший за реалізацію.
- Дані мають одного власника. Інші читають через інтерфейс чи подію.
- Залежності спрямовані до стабільнішого: бізнес-правила не залежать від бази чи вебу.

Ознаки поганої межі: щоразу зміна одного поля зачіпає кілька модулів; циклічний імпорт; спільний модуль `utils` росте без кінця; модуль читає таблиці іншого.

## Як знайти межі

1. Подивись, що змінюється разом: `git log --name-only --pretty=format: | sort | uniq -c | sort -rn` дасть гарячі файли, а спільні коміти покажуть прихований звʼязок.
2. Склади список понять предметної області. Одне слово з різним значенням у двох місцях (BoundedContext): кандидат на межу.
3. Намалюй карту залежностей інструментом, а не з памʼяті. Рівні C4 (контекст, контейнери, компоненти) досить для розмови.

## Порти й адаптери

Бізнес-логіка оголошує інтерфейс, який їй потрібен (порт). База, HTTP, вендор реалізують його (адаптер). Вигода: логіка тестується без інфраструктури, зовнішню залежність можна замінити. Ціна: додатковий шар. Застосовуй там, де є реальна логіка; для тонких CRUD-обгорток це може бути зайвим.

## Виконувана перевірка меж

Правило без автоматичної перевірки зношується. Приклади:

```ini
# Python: import-linter, файл .importlinter
[importlinter]
root_package = app

[importlinter:contract:layers]
name = Шари
type = layers
layers =
    web
    services
    domain
```

```js
// JS/TS: dependency-cruiser
{ forbidden: [{ name: "no-domain-to-web", from: { path: "^src/domain" }, to: { path: "^src/web" } }] }
```

```java
// Java: ArchUnit
noClasses().that().resideInAPackage("..domain..")
    .should().dependOnClassesThat().resideInAPackage("..web..");
```

Go: `internal/` забороняє імпорт ззовні дерева, компілятор перевіряє сам.

Для перевірки меж теж потрібен негативний тест: навмисно додай заборонений імпорт і подивись, що перевірка впала.

## Поступовий перехід

| Прийом | Коли | Суть |
|---|---|---|
| Strangler fig | заміна системи | новий шлях обгортає старий, частка трафіку росте, старе відмирає |
| Branch by abstraction | заміна компонента всередині | ввести абстракцію, під нею дві реалізації, перемкнути, прибрати стару |
| Parallel run | ризиковане обчислення | дві реалізації паралельно, порівняння виходів, результат зі старої |
| Feature toggle | поступове ввімкнення | новий шлях за прапорцем, прапорець має дату видалення |
| Expand-contract | дані й API | навичка `data-migrations` |

Критерій кроку: кожен окремо потрапляє в main і випускається; якщо зупинитись після нього, система все одно робоча.

## Рефакторинг

- Окремий коміт від зміни поведінки.
- Перед змінами: характеризаційні тести, якщо тестів немає.
- Малі кроки з прогоном тестів між ними.
- Перед рефакторингом випиши, яку зміну він полегшує. Без цього це витрата.

## Спільний код

Спільний модуль варто витягувати після другого чи третього реального випадку. Передчасна спільна абстракція звʼязує різні речі, що лише схожі сьогодні. Копії, що повинні лишатися однаковими, є окремим ризиком: перенось в один пакет або генеруй з одного джерела.
