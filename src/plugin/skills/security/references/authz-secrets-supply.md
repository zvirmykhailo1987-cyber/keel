# Авторизація об'єкта, секрети, ланцюг постачання

## Авторизація на рівні об'єкта (IDOR, BOLA)

Дефект: застосунок перевіряє, що користувач увійшов, але не перевіряє, що цей об'єкт належить йому. Сканери його майже не бачать: запит виглядає нормальним.

### Метод

1. Знайди всі обробники, що приймають ідентифікатор: у шляху, query, тілі, заголовку, GraphQL-аргументі, повідомленні черги.
2. Заповни таблицю. Кожен рядок має доказ.

| Маршрут | Об'єкт | Перевірка власника | Читання/запис | Негативний тест |
|---|---|---|---|---|
| GET /invoices/{id} | Invoice | `invoices.py:44` | читання | є |

3. Перевір окремо: читання, зміну, видалення, експорт, вкладені об'єкти (`/orgs/{a}/projects/{b}`: чи належить `b` до `a`?), пакетні операції, пошук, завантаження файлів за прямим посиланням.
4. Негативний тест на шаблон: користувач B звертається до об'єкта A, очікується 403 або 404.

### Як правильно

Шукай об'єкт через власника, а не перевіряй після отримання:

```python
# Django
Invoice.objects.get(pk=id, owner=request.user)
```

```js
// SQL: Node
pool.query("SELECT * FROM invoices WHERE id = $1 AND tenant_id = $2", [id, tenantId])
```

- Контекст орендаря бери із сесії, а не з параметра запиту.
- Для багатьох орендарів розглянь обмеження на рівні бази, наприклад Row Level Security у PostgreSQL. Обмеження лише в промпті моделі чи лише в інтерфейсі не є захистом.
- Непередбачувані id (UUID) ускладнюють перебір, але не замінюють перевірки.
- Спільна функція чи політика краща за перевірку, скопійовану в кожен обробник.

### Ролі й підвищення

Горизонтальне: ті самі права, чужий об'єкт. Вертикальне: звичайний користувач викликає адмінську дію, надсилає поле `is_admin`. Матриця «роль × дія» з тестами є найкоротшим доказом.

## Секрети

### Три стани

| Стан | Що означає | Дія |
|---|---|---|
| у git зараз | аварія | винести негайно й ротувати (людина) |
| був у git, прибраний | скомпрометований: історія лишилась | ротація, запис події (людина) |
| ніколи не був у git | норма | підтримувати |

Другий стан виглядає розвʼязаним, але таким не є. Видалення файла не змінює того, що значення читали всі, хто клонував репозиторій. Переписування історії не допомагає тим, хто вже має копію, тому головне лікування: ротація.

### Метод

1. Скан робочого дерева: `sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel scan .` (шлях обовʼязковий: без нього сканувати нічого й звіт буде порожнім).
2. Скан історії: `gitleaks git`. Цього немає в рушії: він перевіряє файли й індекс, а не історію.
3. Також перевір: логи, CI-змінні у виводі, образи контейнерів (`ENV`, шари), приклади `.env.example`, фронтенд-бандл, source map.
4. Зберігай у змінних оточення чи менеджері секретів; локальні файли в `.gitignore`.
5. Застосунок падає при старті без обовʼязкового секрету: дефолт у коді заборонено.
6. Ротація є подією із записом: що, коли, чи старе значення більше не діє. Виконує людина.

### Гейт

Pre-commit блокує нові витоки. Хибна тривога означає лагодити гейт, а не обходити: гейт із частими хибними тривогами швидко вимикають.

## Ланцюг постачання

### Нова залежність

Перед додаванням:

1. Чи потрібна? Кілька рядків свого коду іноді безпечніші за пакет.
2. Чи справді існує такий пакет? Імʼя від моделі може бути вигаданим, а зловмисник може зареєструвати саме таке (slopsquatting, typosquatting). Перевір у реєстрі: автор, вік, завантаження, репозиторій.
3. Хто підтримує, коли останній реліз, чи є звіт OpenSSF Scorecard.
4. Чи є install-скрипти: вони виконуються при встановленні.

Популярність сама не є доказом безпеки.

### Закріплення й встановлення

| Екосистема | Встановлення за lockfile |
|---|---|
| npm | `npm ci` |
| pnpm | `pnpm install --frozen-lockfile` |
| Python | `pip install --require-hashes -r requirements.txt`, `uv sync --locked` |
| Rust | `cargo build --locked` |
| Go | `go.sum`, `go mod verify` |
| .NET | `dotnet restore --locked-mode` |
| Ruby | `bundle install` з `BUNDLE_FROZEN=true` |

Екшени CI закріплюй повним SHA (навичка `deploy-ci`).

### Аудит

- Команда `audit` профілю стеку для вразливостей.
- OSV-Scanner для кількох екосистем.
- Для образів: Trivy.
- SBOM на випуск, якщо потрібен споживачам: Syft, формат CycloneDX.

Фальшиву тривогу аудиту перевір досяжністю: чи виконується вразливий виклик. Винятки записуй із причиною й датою перегляду, а не вимикай правило повністю.

### Відповідь на компрометацію пакета

1. Встанови, чи була уражена версія в lockfile й чи встановлювалась у CI.
2. Припини випуски, закріпи безпечну версію.
3. Вважай секрети з ураженого середовища скомпрометованими: ротація людиною.
4. Запиши хронологію, подальші дії вирішує людина.
