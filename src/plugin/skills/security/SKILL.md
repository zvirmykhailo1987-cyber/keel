# security: загроза з конкретним шляхом атаки, а не загальні поради

Якщо в pre-flight сесії згадано overlay для цієї навички, прочитай його перед роботою.

## ТЗ-чекліст

«Перевір безпеку» означає пакет. Веди N/N до кінця.

1. Модель загроз коротко: активи, дійові особи, точки входу, межі довіри.
2. Кожен маршрут чи обробник із ідентифікатором об'єкта перевірено на авторизацію (перелік із числом).
3. OWASP Top 10 пройдено за `references/owasp-checklist.md`: статус кожного пункту.
4. Секрети: скан робочого дерева й історії, стан кожного знайденого.
5. Залежності: аудит вразливостей, lockfile, походження нових пакетів.
6. Негативні тести на знайдені дірки.
7. Знахідки подано зі шляхом атаки, серйозністю, виправленням.
8. Tier 3 дії перелічено для людини, а не виконано.

## Pre-flight

Прочитай у `${CLAUDE_PLUGIN_ROOT}/data/pitfalls/`:

- G3 секрети в репозиторії; G22 мовчазний дефолт; G6 документація розходиться з кодом.
- G20 перевірка дивиться не туди; G21 гейт із хибними тривогами вимикають; G60 техніка пройшла, а задумане не відбувається.
- G58 чужий скіл, промпт чи пакет ставиться лише через популярність; G44 важливе живе лише на диску; G19 бекап без маніфесту.

## Метод

1. **Побудуй карту.** Точки входу (HTTP, черги, вебхуки, CLI, завантаження файлів), активи, ролі, межі довіри. Для ідентифікації маршрутів користуйся маршрутизатором фреймворку, а не документацією.
2. **Авторизація об'єкта передусім:** порушення контролю доступу посідає A01 в OWASP Top 10 2025, а BOLA перше місце в API Security Top 10 2023. Склади таблицю: маршрут, об'єкт, де перевірено власника, тест. Деталі в `references/authz-secrets-supply.md`.
3. **Пройди решту пунктів OWASP** за чеклістом. Статус кожного: перевірено, чисто / знахідка / не перевірено з причиною. «Не застосовно» теж обґрунтовуй.
4. **Секрети.** Запусти скан рушія по робочому дереву, потім окремо перевір історію (`gitleaks git`). Секрет, що побував у git, вважається скомпрометованим, навіть якщо його вже прибрано.
5. **Ланцюг постачання.** Запусти `audit` із профілю; перевір наявність і використання lockfile; для нових залежностей: імʼя, вік, підтримка, install-скрипти; перевір екшени CI. Radar плагіна показує вразливості за lockfile: якщо джерело не відповіло, це «не перевірено», а не «чисто». Твердження про пакет чи вендора перевіряй цитатою:

   ```sh
   sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel verify-fact "<URL>" "<дослівна цитата>"
   ```

6. **Знахідки підтвердь експлуатацією в локальному оточенні,** де це безпечно: запит від імені чужого користувача чи payload в тест. Лише свій застосунок, ніколи чужі системи.
7. **Виправлення з тестом.** Кожна закрита діра отримує негативний тест, що падав до виправлення.
8. **Звіт.** Кожна знахідка: де (`file:line` або маршрут), шлях атаки, наслідок, серйозність, виправлення. Найсерйозніші зверху. Окремо: що не перевірено й що чекає на людину.

### Формат знахідки

```text
SEC-3 | critical | src/api/invoices.py:44 | GET /invoices/{id}
Шлях: користувач A підставляє id рахунку B; запит шукає лише за id.
Наслідок: читання чужих рахунків і персональних даних.
Виправлення: шукати за (id, owner_id), 404 на чуже; негативний тест.
```

## Профіль стеку

Команду аудиту бери з `.keel/project.toml` і `${CLAUDE_PLUGIN_ROOT}/data/stacks/<id>.toml`, секція `[commands]`, поле `audit`. Там само `frameworks` і `pitfalls`.

Скан секретів:

```sh
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel scan .
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run.sh" -m keel scan --staged
```

Шлях вказуй завжди: без нього сканувати нічого, і звіт порожній. Сканер ловить відомі формати й присвоєння, а не все: це страховка, а не гарантія. Кажи про це у звіті.

Параметризований запит за мовою:

- Python: `cur.execute("SELECT * FROM t WHERE id = %s", (id,))`
- Node: `pool.query("SELECT * FROM t WHERE id = $1", [id])`
- Go: `db.Query("SELECT * FROM t WHERE id = $1", id)`
- Java: `PreparedStatement` із `setLong(1, id)`
- PHP: PDO `prepare` + `execute([$id])`

Плейсхолдер залежить від драйвера.

## Автономія

| Дія | Tier | Хто |
|---|---|---|
| Читання коду, скан, аудит залежностей, модель загроз | 0 | авто |
| Виправлення з негативним тестом, локальна гілка; локальна перевірка власного застосунку | 1 | авто |
| Сканування чи перевірка робочого сервера й будь-яких чужих систем | 3 | людина, лише з дозволу власника |
| Ротація секретів, переписування історії git, відкликання токенів | 3 | лише людина |
| Push у main, деплой, публікація, міграція робочої бази, гроші, листи (зокрема про витік) | 3 | лише людина |

Секретів не читай і не проси вставити в чат. Потрібне значення: нехай людина внесе його в середовище сама. Знайдений секрет не повторюй у звіті: лише файл, рядок, тип.

## Типові збої

- Перевірка прав лише в інтерфейсі чи лише в списку об'єктів → обробник із id лишився відкритим.
- Роль перевірено, а власника ні → горизонтальне підвищення привілеїв.
- Секрет прибрано з файла й задачу закрито → він досі в історії; потрібна ротація.
- Звіт із 50 пунктів без шляхів атаки → ніхто не виправляє; давай шлях і наслідок.
- Зелений сканер як доказ безпеки → інструмент не бачить логічних помилок доступу.
- Власна криптографія чи власне зберігання паролів → замінити перевіреною бібліотекою.
- Виправлення лише одного обробника → той самий патерн у сусідніх лишився.

## Спростування

Назви щонайменше один сценарій, за якого виправлення ламає наявну поведінку: сервісні інтеграції без власника об'єкта, наявні сесії після зміни cookie, старі клієнти після жорсткішої валідації, адміністративний доступ. Для висновку «чисто» назви, який клас атак перевірка не покриває.

## Гейт «готово»

- Запущено: команди скану й аудиту, код виходу, число знахідок.
- Виміряно: таблиця авторизації N/N обробників, статус 10 пунктів OWASP.
- Негативні тести на закриті дірки падають без виправлення.
- Не перевірено: скажи явно (історію не скановано, DAST не запускався, не бачив конфігурації сервера, джерело вразливостей не відповіло).
- Ніколи не пиши «безпечно» без рамок. Формула: «у межах перевірених пунктів знахідок немає; не перевірено: ...».

## Ретро

Після аудиту чи інциденту оформи урок через `/keel:retro`. Повторний клас дірок перетвори на автоматичну перевірку: правило статичного аналізу чи негативний тест.
