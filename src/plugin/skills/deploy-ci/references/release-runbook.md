# Ранбук випуску

Кожен рядок готується заздалегідь. Tier 3 виконує людина.

## Перед випуском

- [ ] Коміт: `<sha>`; CI зелений, посилання на прогін.
- [ ] Артефакт зібрано раз із цього коміту: образ за дайджестом `sha256:...`, не за тегом.
- [ ] Що змінюється: перелік, міграції, нові змінні оточення.
- [ ] Обовʼязкові нові змінні вже додано на сервері.
- [ ] Зʼясовано, хто на звʼязку, і час із низьким навантаженням.
- [ ] Показники до випуску записано: частка помилок, затримка.
- [ ] Умови відкату записано числами.

## Бекап

Бекап перед міграцією є окремим артефактом:

```text
db_2026-11-06_pre-migration-0042.dump
manifest: таблиці N, рядків у ключових таблицях, розмір, sha256, час, версія рушія
```

Перевірка:

1. Хеш збігається.
2. Копія відновлена на окремий екземпляр.
3. Застосунок піднявся на копії й читає записи. Перевірка «файл існує» не рахується.
4. Маніфест повноти: бекап покриває все, а не лише базу. Завантаження, конфігурація, ключі шифрування зберігаються окремо, захищено. Без ключів зашифрований бекап не відновити.

Бекап поза тим самим диском чи сервером. Зберігання: N останніх плюс щомісячні. Журнал відновлення: дата, хто, тривалість.

## Послідовність

| Крок | Дія | Перевірка | Якщо ні |
|---|---|---|---|
| 1 | Бекап | маніфест, хеш | стоп |
| 2 | Міграція expand | лічильники до/після | діяти за планом відновлення, стоп |
| 3 | Випуск нового коду, частка трафіку якщо є | версія у відповіді збігається | відкотити випуск |
| 4 | Smoke-тест | усі перевірки зелені | відкотити випуск |
| 5 | Спостереження 15–30 хв | умови відкату не спрацювали | відкотити випуск |
| 6 | Завершення | запис у журналі | |
| 7 | Міграція contract, окремий пізніший випуск | старого коду ніде немає | не виконувати |

## Перевірка готовності

Розрізняй:

- **Liveness:** процес живий. Падіння означає перезапуск. Не перевіряй залежності тут: відмова бази перезапустить усе.
- **Readiness:** може обслуговувати трафік. Перевіряє базу та інше критичне. Падіння прибирає екземпляр із балансування.
- **Версія:** `/version` чи заголовок, щоб довести, що відповідає саме новий випуск.

Health-check не замінює smoke-тест.

## Smoke-тест

Скрипт, що читає базовий URL і токен лише з оточення. Токен окремого сервісного тестового акаунта без прав на реальні дії.

```sh
#!/bin/sh
set -eu
: "${BASE_URL:?потрібно вказати BASE_URL}"
: "${EXPECTED_VERSION:?потрібно вказати EXPECTED_VERSION}"
version=$(curl -fsS --max-time 10 "$BASE_URL/version")
[ "$version" = "$EXPECTED_VERSION" ] || { echo "версія $version, очікувалась $EXPECTED_VERSION"; exit 1; }
curl -fsS --max-time 10 -o /dev/null "$BASE_URL/healthz"
# далі: вхід тестовим акаунтом, одне ключове читання, один безпечний запис
```

Вимоги: код виходу, таймаут, очікування завершення випуску спершу (опитування з лімітом), не лише «200»: перевір фрагмент очікуваного вмісту. Порожня сторінка теж віддає 200.

## Умови відкату

Приклад, підстав власні базові значення:

| Показник | База | Поріг |
|---|---|---|
| 5xx | 0,2% | понад 1% протягом 5 хв |
| p95 | 300 мс | понад 800 мс протягом 10 хв |
| Smoke | зелений | будь-який збій |
| Ключова бізнес-подія | N за годину | падіння вдвічі |

Числа наведено для прикладу, а не як норма. Немає бази: запиши показники перед випуском.

## Відкат

1. Рішення: хто приймає, за якою умовою. Не сперечатись під час аварії.
2. Команда перевипуску попереднього артефакту: конкретний дайджест.
3. Перевірка версії й smoke.
4. Міграція: чи сумісна стара версія коду з поточною схемою? Так, бо contract ще не виконано. Ні: план B.
5. Запис події й подальший постмортем.

Відновлення бази лише за необхідності: записи після бекапу втрачаються. Це окреме рішення людини.

## Після випуску

- Журнал: версія, час, хто, що вийшло, час smoke.
- Задача на міграцію contract, прибирання прапорця.
- Зазначено, що автоматизовано, а що ще ручне.
- Заплановані задачі: доказ життя є запис про успішний прогін, а не факт реєстрації. Монітор з пульсом сповістить, коли задача перестала запускатись.
