title: Інструмент виміру бреше в Git Bash
---
**Симптом:** `grep -c $'\r' файл` показує CR у кожному рядку файла, у якому їх немає. На такому вимірі ледь не «спростовують» правильний урок.
**Корінь:** текстові утиліти Git Bash на Windows трактують `\r` інакше, ніж на Linux. Число не калібрували на відомому зразку.
**Правило:** керівні байти (CR, BOM, NUL) рахувати лише байтами Python у режимі `rb`, а не `grep`, `wc`, `file` чи `cat -A`. Перед висновком «урок спростовано» потрібен контрвимір іншим інструментом і свідок на відомому зразку. Числа про кодування від автоматичного аудиту позначати «потребує контрвиміру».
**Перевірка:** `printf 'a\r\nb\r\n' > w.txt` і `python -c "print(open('w.txt','rb').read().count(b'\r'))"` дає 2, а файл із LF дає 0. Лише після цього вимірювати реальний.
**Приклад:** аудит каже «усі файли CRLF, але працюють, отже правило хибне». Контрвимір байтами: 0 CR в усіх. Правило лишається, виправляється прилад.
